# LLM-Powered FileSystem Assistant

A project that builds the foundation for an LLM-powered assistant capable
of reading, listing, writing, and searching resume files (`.txt`, `.md`, `.pdf`,
`.docx`).

- **Part A** ships a clean, testable **tool layer** — plain Python functions
  with uniform, JSON-serializable return shapes.
- **Part B** wires those tools into an LLM (OpenAI) so a user can drive them
  with natural-language queries like *"find resumes mentioning Python"*.

Requires **Python 3.8+**.

```powershell
# From the project root
py -m pip install -r requirements.txt
```

Dependencies:

| Package        | Why |
|----------------|-----|
| `pypdf`        | Extract text from `.pdf` files |
| `python-docx`  | Extract text from `.docx` files |
| `openai`       | LLM client used by Part B (`llm_file_assistant.py`) |

`pypdf`, `python-docx`, and `openai` are imported **lazily**, so
`fs_tools.py` still loads without them — you only get a friendly error if you
actually try to read a PDF/DOCX (or launch the LLM assistant) without the
library installed.

## The 4 tools

Every tool returns a JSON-serializable `dict` (or `list[dict]`) that always
includes a `success` flag. Errors follow a consistent envelope:

```json
{ "success": false, "error": "human-readable message" }
```

That uniform shape is exactly what OpenAI/Anthropic tool-calling APIs expect
you to feed back to the model.

### 1. `read_file(filepath: str) -> dict`

Reads a `.txt`, `.md`, `.pdf`, or `.docx` file and returns its text plus
metadata.

**Arguments**

| Name       | Type | Description |
|------------|------|-------------|
| `filepath` | str  | Path to the file to read |

**Returns (on success)**

```json
{
  "success": true,
  "content": "…full extracted text…",
  "metadata": {
    "name": "resume.txt",
    "path": "C:\\…\\resume.txt",
    "size_bytes": 308,
    "modified": "2026-08-15T12:14:16",
    "extension": ".txt",
    "char_count": 296,
    "line_count": 13
  }
}
```

**Behavior**

- `.txt` / `.md` → UTF-8 with a latin-1 fallback so odd bytes never crash.
- `.pdf` → per-page text via `pypdf`.
- `.docx` → concatenated paragraphs via `python-docx`.
- Unsupported extensions return an error envelope listing supported types.

---

### 2. `list_files(directory: str, extension: str = None) -> list`

Lists files in `directory` (non-recursive), optionally filtered by extension.

**Arguments**

| Name        | Type | Description |
|-------------|------|-------------|
| `directory` | str  | Directory to scan |
| `extension` | str  | Optional filter. Accepts `"pdf"`, `".pdf"`, `".PDF"` — all normalized |

**Returns**

A list of file entries, sorted by name:

```json
[
  {
    "name": "resume.pdf",
    "path": "C:\\…\\resume.pdf",
    "size_bytes": 544,
    "modified": "2026-08-15T12:16:04",
    "extension": ".pdf"
  }
]
```

If the directory does not exist / is not a directory, a single-element list
containing an error envelope is returned (keeps the shape JSON-friendly).

---

### 3. `write_file(filepath: str, content: str) -> dict`

Writes `content` (UTF-8) to `filepath`, creating any missing parent
directories automatically.

**Arguments**

| Name       | Type | Description |
|------------|------|-------------|
| `filepath` | str  | Destination path |
| `content`  | str  | Text to write (empty string is allowed) |

**Returns (on success)**

```json
{
  "success": true,
  "path": "C:\\…\\output\\notes.txt",
  "bytes_written": 35
}
```

**Behavior**

- Parent folders are created with `mkdir(parents=True, exist_ok=True)`.
- Refuses to overwrite a path that is currently a directory.

---

### 4. `search_in_file(filepath: str, keyword: str, context_chars: int = 60) -> dict`

Case-insensitive substring search inside a file. Works on any format
`read_file` supports (so you can search inside PDFs and Word documents too).

**Arguments**

| Name            | Type | Description |
|-----------------|------|-------------|
| `filepath`      | str  | File to search |
| `keyword`       | str  | Substring to look for (case-insensitive) |
| `context_chars` | int  | Chars of surrounding context per match (default 60) |

**Returns (on success)**

```json
{
  "success": true,
  "keyword": "python",
  "filepath": "C:\\…\\resume.txt",
  "match_count": 3,
  "matches": [
    {
      "line": 2,
      "position": 16,
      "match": "Python",
      "context": "Jane Doe Senior Python Developer  Experience: - 6 years of Python …"
    }
  ]
}
```

`line` is 1-based; `position` is the 0-based character offset into the raw
extracted text.

## Running the smoke tests

The test script generates its own sample `.pdf` and `.docx` on the fly (no
binary assets needed in the repo) and then exercises every tool.

```powershell
py tests\test_fs_tools.py
```

You should see 10 test blocks succeed:

1. `list_files` — all files
2. `list_files` — filtered by `pdf`
3. `read_file` — `.txt`
4. `read_file` — `.pdf`
5. `read_file` — `.docx`
6. `write_file` — auto-creates `output/`
7. `search_in_file` — `.txt`, case-insensitive
8. `search_in_file` — inside a `.docx`
9. Error case — file not found
10. Error case — unsupported extension

> Note: if `reportlab` isn't installed the PDF test uses a tiny hand-rolled
> fallback PDF. `pypdf` will print an `incorrect startxref pointer(1)` warning
> for that file — it's harmless (text extraction still works). Install
> `reportlab` if you want to silence it: `py -m pip install reportlab`.

|---------------------------------------|-------------------------------------------------------------------------|
| Structured tool interfaces            | Typed args + uniform `{success, …}` dict on every function              |
| File I/O operations programmatically  | `pathlib.Path`, `read_text`, `write_text`, `iterdir`, `stat`            |
| Parse & validate documents            | PDF via `pypdf`, DOCX via `python-docx`, encoding fallback for TXT      |
| LLM function calling (Part B)         | Tool schemas + agent loop in `llm_file_assistant.py`                    |

## Part B — LLM Integration

`llm_file_assistant.py` exposes the 4 tools to an OpenAI chat model. The
model decides which tools to call based on your natural-language query, the
script executes them locally against the filesystem, feeds the results back,
and lets the model produce a final answer.

### Setup

```powershell
# API key (persistent — open a new terminal after running):
setx OPENAI_API_KEY "sk-..."

# Or just for the current PowerShell session:
$env:OPENAI_API_KEY = "sk-..."

# Optional: pick a different model (default is gpt-4o-mini)
$env:OPENAI_MODEL = "gpt-4o-mini"
```

### Verify the setup without spending tokens

```powershell
py llm_file_assistant.py --dry-run
```

This prints the JSON tool schemas and the local dispatcher — no API call is
made. Good for confirming that the schemas are well-formed and every tool
name resolves to a real function.

### Ask a one-off question

```powershell
py llm_file_assistant.py "list all pdf files in sample_data"
py llm_file_assistant.py "find resumes mentioning Python"
py llm_file_assistant.py "create a summary file for sample_data/resume.txt at output/summary_resume.txt"
```

### Interactive REPL

```powershell
py llm_file_assistant.py
```

You'll see each tool the model calls with its arguments and a short result
preview, e.g.:

```
you> find resumes mentioning Python in sample_data
  -> tool: list_files({'directory': 'sample_data'})
     result: [{"name": "resume.docx", ...}, {"name": "resume.pdf", ...}, ...]
  -> tool: search_in_file({'filepath': 'sample_data/resume.txt', 'keyword': 'Python'})
     result: {"success": true, "match_count": 3, ...}

assistant> resume.txt and resume.docx both mention Python…
```

### How the agent loop works

1. Send the user's message + the tool schemas to the model.
2. If the model responds with `tool_calls`, execute each one locally via the
   dispatcher and append `role="tool"` messages containing the JSON results.
3. Loop back to step 1 with the enriched conversation.
4. Stop when the model returns a plain text answer (or after
   `MAX_TOOL_ITERATIONS` = 8, as a safety net).
